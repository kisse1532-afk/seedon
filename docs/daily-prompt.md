## 3. 문구 전수 스캔 (신규 등록 전에 먼저)

```sql
select id, title, description, apply_method from programs where status='published'
and (description ~ '저소득|취약계층|결손|차상위|수급자|지원대상자'
  or array_to_string(tags,' ') ~ '저소득|취약계층|결손|차상위|수급자|지원대상자'
  or description ~ '중위소득|소득인정액|가구원|소득분위'
  or description ~ '합니다|됩니다|입니다|하였|을 대상으로'
  or apply_method ~ '중위소득|의뢰서|배분신청|이수|산정|선정');
```

낙인 표현(절대규칙 1)과 행정용어·보도자료 말투(절대규칙 3)를 잡는다. 고칠 때마다 `review_note`에 사유를 남기고 몇 건 고쳤는지 보고할 것.

**걸렸다고 다 고칠 것은 아니다.** `의뢰서`·`이수`·`연계` 같은 말은 **행동으로 풀어썼으면 통과**다 — 절대규칙 3이 제시한 모범 예시 자체가 "Wee센터에 가서 '의뢰서'라는 서류를 받아요"이다. 제도 고유명사를 아예 못 쓰게 하면 청소년이 그 서류를 달라고 말할 수조차 없다. **그 낱말이 설명 없이 툭 튀어나왔을 때만** 고친다. `mindcare-voucher-01`이 매번 여기 걸리는데 이미 규칙대로 쓰여 있으니 손대지 말 것.

## 4. 리서치 — 올리고 내리기 (승인 불필요)

**찾았으면 바로 올린다.** 로드 결정(2026.08.15 저녁): "애가 찾은 걸 바로 올리고 싶어." pending에 쌓아두는 건 실제로는 묵히는 것이었다 — 우리 서버가 못 여는 페이지도 청소년 폰에서는 멀쩡히 열린다. **우리 쪽 방화벽 사정으로 멀쩡한 지원제도를 안 보여주는 게 제일 나쁘다.**

**딱 하나만 지킨다: 확인 못 한 숫자는 쓰지 않는다.** 금액·인원·기간은 기관 자체 도메인에서 직접 본 것만. 못 봤으면 숫자를 빼고 "그해 공고에서 확인하세요"로 두고 **게시한다.** 사업을 묵히지 말 것.

### 게시 전 체크리스트 (숫자 규칙만 필수, 나머지는 최대한 채운다)

1. **⚠️ 숫자는 공식 페이지에서 직접 본 것만 (이것만 어기면 안 됨)** — 금액·인원·기간. **언론 보도·취합 사이트(위비티·링커리어)의 숫자를 옮기지 말 것.** 못 봤으면 숫자를 빼고 "그해 공고에서 확인하세요"로 두고 **게시한다**
   - **단, 포기하기 전에 `node scripts/read-hwpx.mjs <공고 URL>`을 먼저 돌릴 것.** 공공기관은 내용을 첨부 한글파일에만 넣는 일이 흔하다. 거기서 읽은 숫자는 공식 근거다
2. **사업이 실재하는지** — 기관 자체 도메인에 그 사업이 있는지. 페이지가 403이거나 자바스크립트로만 그려져 못 읽어도, 실재가 확인되면 올린다. `review_note`에 못 연 사유와 근거 URL을 남길 것
3. **링크는 그 프로그램의 신청·안내 페이지** — 기관 대문만 넣지 말 것. 딥링크를 못 찾으면 `link_kind='info'`로 두고 `apply_method`에 "거기 들어가서 뭘 찾아야 하는지"를 행동으로 쓴다. `http://`는 금지
4. **사업명은 공식 페이지에 적힌 그대로** — 기사 제목·애칭을 사업명으로 쓰지 말 것
5. **14세 이상**이 대상에 포함되는지. 청년(19세~) 전용은 등록 금지
6. **⚠️ 청소년이 오늘 할 수 있는 행동이 있는가** — 수혜 대상이 청소년인 것만으론 부족하다. `CLAUDE.md`의 "게시 기준" 표를 볼 것. 기관 경유여도 **청소년이 먼저 말하면 시작되면 게시**하고, 그 한마디를 `apply_method`에 그대로 적는다("선생님한테 '○○ 받고 싶어요'라고 말해보세요"). **"~할 수 없어요"로 끝내지 말 것** — 반드시 "그러니까 ~해보세요"까지. 행동을 끝내 못 찾으면 내린다
7. **쉬운 말로 다시 쓰기** — 기관 문장을 복사하지 말고 "~해요"체로. 소득 조건은 실제 금액으로 환산하고 "물어볼 곳"을 붙인다
8. **자격요건이 있다는 이유로 빼지 말 것** — 그런 제도일수록 알리는 게 미션이다. 단 조건을 카드 라벨로 달지는 않는다
9. **카테고리** — `CLAUDE.md`의 "카테고리 판정 기준" 표를 볼 것. 판별식은 **돈을 주는 사업이면 "그 돈을 어디에 쓰라고 주는지"**. "멘토링"이라는 말만 보고 진로에 넣는 실수가 실제로 있었다(학습 멘토링은 교육)
10. **중복 확인** — 있으면 새로 만들지 말고 기존 행을 갱신
11. **접수 방식** — `apply_deadline` / `enrollment_status` / `reopen_note` 중 최소 하나

### 접수 방식 판정

| 상황 | 입력 |
|---|---|
| 기간이 정해져 있고 아직 열림 | `apply_deadline` = 공식 페이지에서 확인한 날짜 |
| 연중 본인이 직접 신청 | `enrollment_status='상시 신청'` |
| 신청 절차 없이 그냥 쓰는 것 | `enrollment_status='언제든 이용'` |
| 학교·주민센터·기관 경유만 | `enrollment_status='기관 통해 신청'` |
| 이번 회차 끝남 | `reopen_note` = 다음 모집 안내 |

`enrollment_status`는 위 세 문구 **정확히 그대로**. 날짜를 확인 못 했으면 비워둘 것 — 추측 금지.

- `pending`은 **사업이 실재하는지조차 불확실할 때만.** "페이지를 못 열었다"는 pending 사유가 아니다 — 숫자만 빼고 올릴 것

**지자체·문화체험·공모전·마감일 있는 모집형을 우선.** 지금 가장 빈약하다.

### 내릴 때

`deleteProgram`(하드 삭제) 금지. `status` 변경으로만. 사업 종료는 `rejected`, 회차 종료는 `reopen_note`. **모든 변경에 `review_note`로 "날짜 + 무엇을 확인했고 왜 바꿨는지"를 남길 것.**

>
> 그전에는 요일마다 한 부서씩이었다. 그렇게 하면 로드가 하루에 한 갈래밖에 못 본다. 운영을 잡으려면 여섯 갈래를 한 번에 놓고 봐야 한다.

**여섯 부서를 동시에 띄운다.** 서로 의존하지 않으므로 순서대로 기다릴 필요가 없다.

**부서를 부를 때 `docs/team-now.md` → `docs/team-context.md` 순으로 먼저 읽으라고 시킬 것.**
부서는 매번 아무것도 모르는 상태로 시작한다. 부서 정의 파일에도 적어뒀지만 부를 때 한 번 더 말해라.

### 디자인팀을 부르기 전에 화면을 찍어둘 것 (2026.08.18 신설)

디자인팀에는 브라우저가 없다. 그래서 여태 **코드만 읽고 "이렇게 보일 것"이라고 추정**해
보고했고, 카톡 로고가 붙어 보인다는 지적에 네 번 연속 틀린 답을 한 사고가 그래서 났다.

부르기 **전에** 이걸 돌려 그림을 만들고, 그 경로를 프롬프트에 적어줘라:

```
# 로컬로 띄운 다음 찍는다 (배포 주소는 못 찍는다 — 아래 이유 참고)
NODE_USE_ENV_PROXY=1 npm run start &
node scripts/shot.mjs http://127.0.0.1:3000/ /category/housing /apply/edu-01 \
  --widths 390,1000 --out .shots
```

**배포 주소(`https://seedon.vercel.app`)는 못 찍는다.** 이 환경의 바깥 통신은 프록시를
거치는데 크롬이 그 프록시를 못 쓴다(`--proxy-server`를 줘도 ERR_CONNECTION_RESET,
example.com도 똑같이 실패하니 우리 사이트 문제가 아니다 — 2026.08.18 확인).
**로컬로 띄워서 찍으면 된다.** 배포본이 아니라 지금 코드를 보는 것이라 리뷰용으로는
오히려 이게 맞다. 도구가 바깥 주소를 받으면 미리 경고해준다.

- **폰 폭(390)을 반드시 포함한다.** 청소년은 폰으로 본다
- 그림 맨 위 띠에 폭·테마와 **가로 밀림 여부**가 찍혀 나온다
- 그날 만든 브리핑 HTML도 올리기 전에 이걸로 찍어 확인한다
  (`node scripts/shot.mjs docs/daily/YYYY-MM-DD.html --themes light,dark --widths 390`)
- 헤드리스 크롬이 창 크기를 무시하고 485px로 그리는 함정이 있는데, 이 도구가
  iframe으로 감싸서 막아준다. **직접 크롬을 부르지 말고 이 도구를 쓸 것**

| 부서 | 오늘 시킬 것 |
|---|---|
| `planning` (전략기획실) | 지금 씨드온이 다음에 해야 할 한 가지. 사업계획서·투자·수익 구조 중 지금 단계에 맞는 것 |
| `bizops` (사업운영) | 기능이 실제로 도는지, 홈페이지에 고칠 곳이 있는지. 기획실 방향이 있으면 과제로 쪼개기 |
| `design` | UI/UX 벤치마킹 + 아이덴티티에 안 맞는 곳 + 브랜드 규칙 |
| `research` | 새 프로그램 발굴 + 등록된 카드 사실 재확인 |
| `marketing` | 소셜벤처가 어떻게 알렸는지 조사해 쌓기 (실행 제안은 아직 하지 않는다) |
| `support` | 도움요청·후기가 오면 어떻게 답할지 준비 (데이터 0건이면 "없음"으로 끝내도 됨) |

- **볼 게 없으면 "없음"으로 짧게 끝내게 한다.** 억지로 일을 만들면 브리핑이 길어지고, 길어지면 로드가 안 읽는다. 그게 제일 나쁘다
- **보고가 안 온 부서는 "보고 없음"이라고 그대로 쓴다.** 2026.08.16에 CS·사업팀 보고가 안 왔는데 표를 채우려고 내용을 지어낸 사고가 있었다. **빈칸이 거짓말보다 낫다**
- 부서를 부르면 토큰을 쓴다. 그래도 매일 돌리는 건 **로드가 운영을 잡는 게 그보다 중요하다는 판단**이다(로드 결정)

### 부서 보고를 반영하는 법 (7단계 검수 규칙)

부서에게는 쓰기 도구가 없다. 올리고 고치는 건 전부 실장이 한다. 그래서 **부서 보고를 그대로 옮기면 검수가 사라진다.**

1. 보고에 적힌 **근거 URL을 실장이 직접 연다.** 못 열면 반영하지 않고 "못 열었다"고 적는다
2. **숫자는 특히 다시 본다.** 2026.08.15에 검색 결과를 근거로 없는 사업·없는 금액을 올린 사고가 이래서 났다
3. 반영한 것과 반려한 것을 `review_note`에 남긴다 — 무엇을 확인했고 왜 그렇게 정했는지
4. 브리핑에 부서별로 "제안 O건 → 반영 O건, 반려 O건(사유)"을 적는다

## 6. 통합 브리핑 — 로드가 읽고 지시하는 문서

**이게 데일리의 결과물이다.** 부서 보고를 실장이 검수한 뒤 **하나로 합쳐서** 낸다. 여섯 개 보고를 그대로 붙여놓는 건 브리핑이 아니다.

### 어디에 내나

1. **아티팩트(Artifact)로 만들어 링크를 준다.** (2026.08.16 로드 확정:
   *"아티팩트에 올리면 바로 볼 수 있어서 괜찮아."*)
   `docs/daily/_TEMPLATE.html`을 복사해 그날 내용으로 채우고 `Artifact` 도구로 올린다.
   - **`SendUserFile`은 여전히 쓰지 말 것.** 파일은 내려받아 여는 단계가 붙는다.
     아티팩트는 링크를 누르면 바로 뜨므로 그 단계가 없다 — 그래서 허용된 것이다
   - 올리기 전에 **라이트·다크·폰 세 가지로 직접 찍어 확인한다.** 가로로 밀리면 안 됨
     (`scratchpad/shot.mjs` 방식). 실제로 폰에서 전화번호가 두 줄로 잘린 적이 있다
   - 매일 **같은 파일 경로로 새로 올린다** — 날짜별로 URL이 따로 생겨야 되짚을 수 있다
2. **대화창에는 결론과 정할 것만 짧게 쓰고 링크를 붙인다.** 링크만 툭 던지지 말 것 —
   로드가 링크를 안 눌러도 "오늘 뭐가 제일 중요한지"는 알 수 있어야 한다
3. `docs/daily/YYYY-MM-DD.html`로 저장하고 커밋 — 나중에 되짚을 기록
4. 노션 MVP 현황 페이지에 "## YYYY.MM.DD 데일리"로 append (텍스트 요약 + 아티팩트 링크)

### 쓰는 법 — 두괄식. 표를 나열하는 건 보고가 아니다

로드 지적(2026.08.16): *"지금 보고는 뭔말인지 너무 흩어져 있어. 알아듣기가 어려워."*

처음 낸 브리핑이 🔴🟡📊🏢⚪ 다섯 구역에 표를 여섯 개 늘어놓은 것이었다. **정보는 다 있는데 "그래서 무슨 말인가"가 없었다.** 읽는 사람이 여섯 표를 다 읽고 스스로 결론을 만들어야 하는 문서는 보고서가 아니다.

**순서를 이렇게 쓴다.**

```
1. 결론          오늘 상태를 한 문장으로. "막힌 건 X다"
                 그 밑에 그 판단의 근거가 되는 숫자 두세 개만
2. 그래서 정할 것  가장 중요한 것 하나를 크게. 추천을 먼저 말하고 이유를 뒤에
3. 나머지 결정     사소한 건 묶어서 한 줄씩. "→ 그냥 할까?"
4. 오늘 한 일      제안 O건 → 반영 O건, 반려 O건. 눈에 띄는 것 3~4줄만
5. 로드가 할 일     목록. 그중 1번 결론과 이어지는 게 있으면 그것만 짚어준다
```

**지킬 것**

- **⚠️ "정할 것" 자리에 심부름을 올리지 마라 (2026.08.18 로드 지적).**
  로드: *"검수만 하는 게 아니라 방향을 제시해줄 수도 있어야 될 거 같은데?"*

  그날 브리핑에서 로드에게 낸 "오늘 정할 것 하나"가 **엑셀 파일 하나 내려받아
  달라는 부탁**이었다. 하루치 판단을 요청하는 자리에 잡무를 올린 것이다.
  부서 보고를 검증하고 거르는 일에만 자리를 잡으면 매일 "무엇이 틀렸나"는
  나오는데 **"그래서 어디로 가야 하나"는 아무도 말하지 않게 된다.**

  - **1번 결론은 부서 보고 요약이 아니라 실장 본인의 판단이어야 한다.**
    "부서가 이런 걸 올렸습니다"가 아니라 "제가 보기엔 지금 이쪽입니다"
  - **"정할 것"은 방향이나 우선순위여야 한다.** 파일 받아주기·키 넣어주기 같은
    잡무는 "로드가 할 일" 목록으로 내린다. 그건 정할 게 아니라 그냥 할 일이다
  - 판단이 틀리면 로드가 자른다. **틀릴까 봐 안 내는 게 더 나쁘다**
- **결정할 것은 하나로 좁힌다.** 셋을 나란히 놓으면 셋 다 안 정해진다. 오늘 제일 중요한 하나를 고르고 나머지는 "이건 그냥 할까요?"로 내린다
- **표는 비교할 게 둘 이상일 때만.** 한 줄로 쓸 수 있으면 문장으로 쓴다
- **숫자는 판단에 필요한 것만.** 다 보여주는 건 성실한 게 아니라 떠넘기는 것이다
- **근거·과정은 인용문(>)으로 접어 둔다.** 본문에는 결론만
- 구역 나누기용 이모지를 쓰지 않는다. 색이 많으면 오히려 안 읽힌다

### 길이

**A4 한 장 분량을 넘기지 않는다.** 길어지면 안 읽히고, 안 읽히면 지시가 안 나오고, 지시가 없으면 다음 날 같은 걸 또 물어보게 된다.

## 원칙

- **확인 못 한 건 못했다고 그대로 말할 것.** 추측·낙관적 보고 금지
- 화면에 찍히는 라벨은 전부 "이게 사실인가"를 통과해야 한다

- "Do things that don't scale" — 과도한 리팩토링 금지
- 스코프: 씨드온은 "정보 비대칭·접근 장벽 제거"까지만
