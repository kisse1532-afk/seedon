## 0. 어제까지 뭐가 있었는지부터 읽는다

**이 세션은 매일 아무것도 모르는 상태로 새로 시작한다.** 어제 대화를 기억하지 못하므로, 일하기 전에 아래를 먼저 읽어 맥락을 되찾을 것.

1. `CLAUDE.md` — 규칙. 특히 절대규칙·사실 확인 규칙·링크 규칙·개발 큐
2. **노션 MVP 현황 페이지** (https://app.notion.com/p/3a748a79bf6c81298d85fa671f365caf) 의 **최근 2~3일치 기록** — 어제 뭘 했고 뭘 못 했는지, 로드가 뭘 기다리고 있는지가 거기 있다
3. `git log --oneline -20` — 최근 무슨 작업이 있었는지
4. **관리자 화면의 `review_note`** — 이전 에이전트가 "다음에 이걸 확인해라"고 남긴 메모. `node scripts/check-programs.mjs`를 돌리면 손봐야 할 것이 한 번에 나온다

어제 "확인 필요"로 남긴 것부터 처리하고 새 일을 시작할 것. 같은 것을 매일 새로 발견하고 매일 다시 미루는 게 제일 나쁘다.

## 1. 점검 도구 세 개부터 돌린다

```
node scripts/check-links.mjs      # 링크가 살아있나
node scripts/check-programs.mjs   # 마감·대상 연령·접수방식·기관 대문 링크·금액 카드
node scripts/verify-facts.mjs     # 사업명·금액이 공식 페이지에 실제로 있나
```

`--fix`를 붙이면 마감 지난 것은 자동 정리된다(`check-programs.mjs --fix`).

**출력 읽는 법**: "확인 못 함"은 "틀렸다"가 아니다. 기관 사이트가 데이터센터 IP를 막거나 자바스크립트로만 그려져 우리 쪽에서만 안 보이는 경우가 절반쯤 된다. **"고쳐야 함"만 손대고 "확인 못 함"은 사람이 볼 목록으로 넘길 것.** 헷갈리면 멀쩡한 프로그램을 내리게 된다.

## 3. 문구 전수 스캔 (신규 등록 전에 먼저)

```sql
select id, title, description, apply_method from programs where status='published'
and (description ~ '저소득|취약계층|결손|차상위|수급자|지원대상자'
  or array_to_string(tags,' ') ~ '저소득|취약계층|결손|차상위|수급자|지원대상자'
  or description ~ '중위소득|소득인정액|가구원|소득분위'
  or description ~ '합니다|됩니다|입니다|하였|을 대상으로'
  or apply_method ~ '중위소득|의뢰서|배분신청|이수|산정|선정');
```

낙인 표현(절대규칙 1)과 행정용어·보도자료 말투(절대규칙 3)를 잡는다. 고칠 때마다 `review_note`에 사유를 남기고 몇 건 고쳤는지 보고할 것.

**걸렸다고 다 고칠 것은 아니다.** `의뢰서`·`이수`·`연계` 같은 말은 **행동으로 풀어썼으면 통과**다 — 절대규칙 3이 제시한 모범 예시 자체가 "Wee센터에 가서 '의뢰서'라는 서류를 받아요"이다. 제도 고유명사를 아예 못 쓰게 하면 청소년이 그 서류를 달라고 말할 수조차 없다. **그 낱말이 설명 없이 툭 튀어나왔을 때만** 고친다. `mindcare-voucher-01`이 매번 여기 걸리는데 이미 규칙대로 쓰여 있으니 손대지 말 것.

## 4. 리서치 — 올리고 내리기 (승인 불필요)

**찾았으면 바로 올린다.** 로드 결정(2026.08.15 저녁): "애가 찾은 걸 바로 올리고 싶어." pending에 쌓아두는 건 실제로는 묵히는 것이었다 — 우리 서버가 못 여는 페이지도 청소년 폰에서는 멀쩡히 열린다. **우리 쪽 방화벽 사정으로 멀쩡한 지원제도를 안 보여주는 게 제일 나쁘다.**

**딱 하나만 지킨다: 확인 못 한 숫자는 쓰지 않는다.** 금액·인원·기간은 기관 자체 도메인에서 직접 본 것만. 못 봤으면 숫자를 빼고 "그해 공고에서 확인하세요"로 두고 **게시한다.** 사업을 묵히지 말 것.

### 게시 전 체크리스트 (숫자 규칙만 필수, 나머지는 최대한 채운다)

1. **⚠️ 숫자는 공식 페이지에서 직접 본 것만 (이것만 어기면 안 됨)** — 금액·인원·기간. **언론 보도·취합 사이트(위비티·링커리어)의 숫자를 옮기지 말 것.** 못 봤으면 숫자를 빼고 "그해 공고에서 확인하세요"로 두고 **게시한다**
   - **단, 포기하기 전에 `node scripts/read-hwpx.mjs <공고 URL>`을 먼저 돌릴 것.** 공공기관은 내용을 첨부 한글파일에만 넣는 일이 흔하다. 거기서 읽은 숫자는 공식 근거다
2. **사업이 실재하는지** — 기관 자체 도메인에 그 사업이 있는지. 페이지가 403이거나 자바스크립트로만 그려져 못 읽어도, 실재가 확인되면 올린다. `review_note`에 못 연 사유와 근거 URL을 남길 것
3. **링크는 그 프로그램의 신청·안내 페이지** — 기관 대문만 넣지 말 것. 딥링크를 못 찾으면 `link_kind='info'`로 두고 `apply_method`에 "거기 들어가서 뭘 찾아야 하는지"를 행동으로 쓴다. `http://`는 금지
4. **사업명은 공식 페이지에 적힌 그대로** — 기사 제목·애칭을 사업명으로 쓰지 말 것
5. **14세 이상**이 대상에 포함되는지. 청년(19세~) 전용은 등록 금지
6. **⚠️ 청소년이 오늘 할 수 있는 행동이 있는가** — 수혜 대상이 청소년인 것만으론 부족하다. `CLAUDE.md`의 "게시 기준" 표를 볼 것. 기관 경유여도 **청소년이 먼저 말하면 시작되면 게시**하고, 그 한마디를 `apply_method`에 그대로 적는다("선생님한테 '○○ 받고 싶어요'라고 말해보세요"). **"~할 수 없어요"로 끝내지 말 것** — 반드시 "그러니까 ~해보세요"까지. 행동을 끝내 못 찾으면 내린다
7. **쉬운 말로 다시 쓰기** — 기관 문장을 복사하지 말고 "~해요"체로. 소득 조건은 실제 금액으로 환산하고 "물어볼 곳"을 붙인다
8. **자격요건이 있다는 이유로 빼지 말 것** — 그런 제도일수록 알리는 게 미션이다. 단 조건을 카드 라벨로 달지는 않는다
9. **카테고리** — `CLAUDE.md`의 "카테고리 판정 기준" 표를 볼 것. 판별식은 **돈을 주는 사업이면 "그 돈을 어디에 쓰라고 주는지"**. "멘토링"이라는 말만 보고 진로에 넣는 실수가 실제로 있었다(학습 멘토링은 교육)
10. **중복 확인** — 있으면 새로 만들지 말고 기존 행을 갱신
11. **접수 방식** — `apply_deadline` / `enrollment_status` / `reopen_note` 중 최소 하나

### 접수 방식 판정

| 상황 | 입력 |
|---|---|
| 기간이 정해져 있고 아직 열림 | `apply_deadline` = 공식 페이지에서 확인한 날짜 |
| 연중 본인이 직접 신청 | `enrollment_status='상시 신청'` |
| 신청 절차 없이 그냥 쓰는 것 | `enrollment_status='언제든 이용'` |
| 학교·주민센터·기관 경유만 | `enrollment_status='기관 통해 신청'` |
| 이번 회차 끝남 | `reopen_note` = 다음 모집 안내 |

`enrollment_status`는 위 세 문구 **정확히 그대로**. 날짜를 확인 못 했으면 비워둘 것 — 추측 금지.

### 건수

- **제한 없음.** 찾은 만큼 올린다
- `pending`은 **사업이 실재하는지조차 불확실할 때만.** "페이지를 못 열었다"는 pending 사유가 아니다 — 숫자만 빼고 올릴 것

### 훑을 곳 (매일 2~3곳씩 돌아가며)

공공 포털(복지로·정부24·e청소년·꿈드림) / 부처(여가부·교육부·복지부·문체부·고용부) / 지자체(광역·기초 공고, 청소년활동진흥센터) / 배분사업(공동모금회·아름다운재단·초록우산·굿네이버스·세이브더칠드런·월드비전) / 기업재단(삼성·현대·LG·SK·하나·신한·KT&G·포스코, 카카오임팩트, 해피빈) / 지역 거점(청소년수련관·문화의집·도서관·복지관)

**지자체·문화체험·공모전·마감일 있는 모집형을 우선.** 지금 가장 빈약하다.

### 내릴 때

`deleteProgram`(하드 삭제) 금지. `status` 변경으로만. 사업 종료는 `rejected`, 회차 종료는 `reopen_note`. **모든 변경에 `review_note`로 "날짜 + 무엇을 확인했고 왜 바꿨는지"를 남길 것.**
