# Part 1. 공통 운영 체계

## 1-1. 조직도

```
로드 (대표 · 최종 의사결정권자 · 유일한 물리 세계 접점)
 └ 실장 (검증 · 반영 실행 · 팀 간 조정)
    ├ 리서치팀      — 무엇을 올릴 것인가
    ├ 디자인팀      — 어떻게 보일 것인가
    ├ 사업운영팀    — 우리가 한 말이 사실인가
    ├ 전략기획실    — 다음에 무엇을 할 것인가
    ├ 마케팅팀      — 어떻게 닿을 것인가
    └ CS팀          — 사용자가 이해했는가
```

**실장의 역할 정의** — 팀 결과를 그대로 믿지 않고 직접 근거를 열어 확인한 뒤 반영한다. 동시에 팀이 막혔을 때 도구로 뚫어주고, 팀 간 인계를 중개한다.

**실장이 하지 말아야 할 것** — 팀 대신 일하기. 실장이 팀 산출물을 직접 만들기 시작하면 팀은 형식이 되고 실장은 병목이 된다. 실장은 **검증·중개·해금**만 한다.

## 1-2. 기본 원칙 — 되돌릴 수 있으면 그냥 한다

**이 체계의 출발점은 승인이 아니라 되돌리기다.**

승인을 기본값으로 두면 실장이 병목이 되고, 팀은 결정을 안 하는 습관이 든다. 그래서 판단 기준을 "누가 승인했는가"가 아니라 **"틀렸을 때 되돌릴 수 있는가"**로 둔다.

**실행 전 조건은 승인이 아니라 롤백 계획이다.** 되돌리는 방법을 한 줄로 적을 수 있으면 실행한다. 못 적으면 그건 되돌릴 수 없는 일이므로 물어본다.

### 세 갈래 분류

| 갈래 | 판단 | 절차 | 예시 |
|---|---|---|---|
| **A. 그냥 한다** | 되돌리면 끝. 그 사이 아무도 안 봄 | 실행 → 사후 보고 | 권한·RLS·환경변수 설정, 컬럼 추가(nullable), 코드 수정·PR·머지, 내부 점검 도구, 브랜치·라벨 |
| **B. 하고 바로 확인한다** | 되돌릴 수 있지만 그 사이 사용자가 볼 수 있음 | 실행 → **당일** 실장 검증 → 틀리면 즉시 롤백 | 프로그램 등록·수정·상태변경, 화면 문구, 카드 표시 |
| **C. 먼저 묻는다** | 되돌릴 수 없음 | 로드 승인 후 실행 | 데이터 하드 삭제, 외부 발송(메일·문자·SNS), 금전 지출, 개인정보 외부 이동, 계정·도메인 해지, 파괴적 스키마 변경(컬럼 삭제·타입 변경), 절대규칙 수정 |

**B의 위험은 시간이다.** 기술적으로는 되돌려지지만, 그 사이에 청소년이 잘못된 정보를 보고 헛걸음하면 그건 못 되돌린다. 그래서 B는 **실행은 하되 검증을 미루지 않는다** — 같은 날 안에 확인한다.

**애매하면 B로 취급한다.** C로 올려 물어보는 게 안전해 보이지만 실제로는 로드의 시간을 쓰는 것이다. C는 위 목록에 적힌 것만이다.

### 롤백 규칙

- **실행 전에 되돌리는 방법을 한 줄로 기록한다.** "이 PR revert" / "이 컬럼 drop" / "status를 published로 되돌림" 수준이면 충분하다
- **작업 단위를 쪼갠다.** 한 PR에 여러 변경을 묶으면 하나만 되돌릴 수 없다
- **하드 삭제는 어떤 경우에도 금지.** 상태 변경으로만 내린다 — 기록이 남아야 되돌릴 수 있다
- **롤백은 사고가 아니다.** 되돌린 횟수로 팀을 평가하지 않는다. 되돌릴 수 없게 만든 것만 문제다

## 1-3. 자율성 등급

위 세 갈래가 기본이고, **등급은 B의 검증 강도만 조절한다.** A는 처음부터 자유이고 C는 끝까지 로드 승인이다.

### 🔵 시작 등급 = **L2** (2026.08.18 로드 결정)

**전 팀이 L0가 아니라 L2에서 시작한다.** 되돌릴 수 있는 일을 승인받느라 멈춰 서는 게 지금 단계에서 더 큰 손해라고 판단했다. 신뢰를 쌓아서 올라가는 게 아니라, **일단 다 해보고 사고가 나면 내린다.**

| 등급 | B 처리 방식 | 승급 조건 | 강등 조건 |
|---|---|---|---|
| **L0** | 실행 → 당일 전건 검증 | — | (강등 도착점) |
| **L1** | 실행 → 당일 표본 검증 (30%) | 4주 연속 반려율 20% 미만 | 사실 오류 1건 → L0 |
| **L2** | 실행 → **주간 요약 검증** | **← 여기서 시작** | 사고 1건 → L1 |
| **L3** | C 일부를 B로 내림 (대외 초안 등). **최종 발송은 어떤 등급에서도 사람** | L2에서 12주 무사고 + 로드 승인 | 사고 1건 → L2 |

### ⚠️ 자동 조임 규칙 — 사용자가 생기면 되돌린다

지금 L2가 안전한 이유는 **보는 사람이 없기 때문**이다. 사용자가 생기면 B의 위험(잘못된 정보를 보고 헛걸음)이 실제가 되므로 자동으로 조인다.

| 조건 | 조치 |
|---|---|
| 사용자 **1명** 발생 | B 검증을 **당일**로 (L2 → 사실상 L1 수준) |
| 사용자 **10명** 돌파 (S1 진입) | 전 팀 **L1로 리셋.** 여기서 다시 쌓아 올라간다 |
| 사고 1건 | 해당 팀만 1단계 강등 |

이 조임은 자동이며 로드 승인이 필요 없다. 실장이 사용자 수를 매일 확인하고 조건 충족 시 즉시 적용한다.

**반려율** = (실장이 되돌린 건수) ÷ (팀이 실행한 건수). 매주 기록한다.

**"사고"의 정의** — 사실과 다른 정보가 사용자 화면에 노출되고 **당일 안에 안 잡힌 것.** 실행 후 바로 잡아 롤백한 건 사고가 아니다. 내부 실수도 사고가 아니다. (2026.08.18 인천 쉼터 2013년 자료 건은 게시 전에 걸렀으므로 사고 아님)

## 1-6. 팀 간 인계 규칙

**지금 없는 것이 이것이다.** 6팀이 전부 실장하고만 이야기하면 조직이 아니라 독립 작업자 6명이다.

```
리서치 ──신규 등록 문구──▶ 사업운영 (약속 검증)
리서치 ──신규 프로그램──▶ CS (예상 질문 작성)
리서치 ──새 필드────────▶ 디자인 (카드 표시 확인)
디자인 ──새로 쓴 문구──▶ 사업운영 (약속인지 판정)
사업운영 ─거짓 발견────▶ 해당 팀 (수정 요구, 최우선)
마케팅 ──사용자 질문──▶ CS (답변 준비)
마케팅 ──기관 반응────▶ 전략기획실 (기회 단서)
전략기획 ─대외자료 요청▶ 마케팅 (자료 제작)
CS ─────못 찾는 정보──▶ 리서치 (등록 우선순위)
CS ─────막히는 화면──▶ 디자인 (개선 요청)
```

**인계 규칙 3개**

1. **인계는 실장을 거친다.** 팀끼리 직접 지시하지 않는다. 실장이 중개하며 인계 내용을 기록한다
2. **받은 팀은 다음 데일리에 처리 여부를 보고한다.** 인계가 증발하는 걸 막는다
3. **사업운영팀의 수정 요구는 최우선이다.** 거짓말이 화면에 떠 있는 상태는 다른 모든 작업보다 급하다

## 1-7. 기록 규칙

- **모든 판단에 근거를 남긴다.** 무엇을 보고 그렇게 판단했는지(URL·파일·화면). 근거 없는 판단은 반려한다
- **못 한 것은 못 했다고 쓴다.** 추측·낙관 보고 금지. "확인 못 함"은 실패가 아니라 정상 상태다
- **되돌리기 가능하게 남긴다.** 왜 내렸는지 기록이 있어야 나중에 되살릴지 판단할 수 있다
- **노션에 남긴다.** 세션은 사라지지만 노션은 남는다. 새 에이전트가 이 기록만 읽고 이어받을 수 있어야 한다

## 1-8. 팀 신설·폐지 기준

**신설** — 아래 셋을 다 만족할 때만.

1. 기존 팀 어디에도 명확히 안 들어가는 책임이 있고
2. 그 일이 주 1회 이상 반복 발생하며
3. 산출물을 정의할 수 있다

**폐지** — 아래 중 하나면 폐지 또는 흡수.

1. 4주 연속 주간 산출물 없음
2. 다른 팀 산출물과 90% 이상 겹침
3. 존재 이유가 된 문제가 해소됨

**주의** — "있으면 좋을 것 같아서" 만드는 팀이 조직을 죽인다. CS팀이 사용자 0명일 때 만들어져 할 일이 없었던 게 예시다.

## 1-9. 사람이 합류할 때

2027년 대학원 이후 공동창업자·팀원이 생기는 것을 전제로 한다. 그때 AI 팀은 사라지지 않고 **역할이 바뀐다.**

| 구분 | AI 팀이 계속할 것 | 사람에게 넘길 것 |
|---|---|---|
| 원칙 | 반복·검증·수집·초안 | 판단·관계·책임·대외 |
| 리서치 | 발굴·링크 점검·문구 스캔 | 기관과의 관계 |
| 디자인 | 점검·일관성 검사 | 방향 결정 |
| 사업운영 | 대조·자동 검출 | 법적 책임 판단 |
| 전략기획 | 정보 수집·달력 관리 | 전략 결정 |
| 마케팅 | 명단·초안 | 실제 커뮤니케이션 |
| CS | 1차 응대·FAQ | 위기 상황 대응 |

**이양 시 산출물** — 각 팀은 언제든 "지금까지 쌓인 것"을 문서 하나로 내놓을 수 있어야 한다. 사람이 그것만 읽고 이어받을 수 있는 상태를 상시 유지한다.

## 1-10. 발전 책무 — 모든 팀이 밖을 본다 (매일)

**지금 조직의 가장 큰 결함은 전부 "굴리는 일"만 한다는 것이다.** 리서치는 올리고, 디자인은 점검하고, 사업운영은 대조하고, CS는 준비한다. 아무도 "다른 데는 이걸 어떻게 하지"를 묻지 않는다. 이러면 서비스는 유지될 뿐 좋아지지 않는다.

**전략기획실만 밖을 보는 구조는 틀렸다.** 디자인의 발전은 전략기획실이 찾아줄 수 없다. 각 팀이 자기 영역에서 밖을 봐야 한다.

### 규칙

**주기: 매일 (2026.12.31까지)** — 2026.08.18 로드 결정. 지금은 사업을 만드는 중이라 유지 속도로는 부족하다. 연말까지 매일 돌리고, **2027.1.1에 주기를 재검토**한다(주간 또는 월간으로 완화).

- **매일 1건: 조사 → 반영.** 각 팀은 매일 자기 영역에서 "다른 데는 어떻게 하나"를 하나 보고, **하나를 실제로 반영한다**
- **"조사했다"는 산출물이 아니다.** 산출물은 **"오늘 반영한 것 1개"**다. 반영 못 했으면 왜 못 했는지 한 줄
- **직접 실행한다.** 전 팀이 L2이므로 A·B에 해당하는 개선은 제안이 아니라 실행이다. 승인을 기다리지 않는다

### 새 기능 상한 없음 — 대신 주말에 몰아서 확인한다 (2026.08.18 로드 결정)

6팀 × 매일이면 하루 6건, 한 달이면 120건이 쌓인다. 여기에 건수 상한을 두는 대신, **매주 토요일 주간 보고로 로드가 한 번에 훑고 아니다 싶은 건 바로 빼는** 방식을 택한다. **속도를 줄이는 게 아니라 되돌리는 속도를 올린다.**

- **상한 없음.** 개선이든 새 기능이든 매일 반영한다
- **로드의 제거권.** 주간 보고를 보고 "이건 빼"라고 하면 **다음 데일리에 즉시 제거**한다. 이유를 묻지 않는다
- **제거도 반영 1건이다.** 빼는 것을 실패로 치지 않는다. 안 쓰는 화면·기능·지침을 걷어내는 것도 그날의 반영으로 인정한다
- **스코프를 넘지 않는다.** 씨드온은 "정보 비대칭·접근 장벽 제거"까지다. 벤치마크에서 좋아 보여도 이 선을 넘는 기능은 가져오지 않는다 (나비얌의 급식카드 인증, 포인트 게임화가 그 예)

### 주간 보고 형식 (매주 토요일)

**맨 위 네 줄이 로드가 볼 전부다.** 나머지는 궁금할 때만 본다. 3분 안에 훑고 "이건 빼"만 말할 수 있어야 한다.

```
[이번 주 씨드온]
숫자   가입 N / 게시 N / 신청 N / 도움요청 N   (지난주 대비 ±)
새 것  N개   ← 뺄 거 있으면 말해줘
결정   로드가 정할 것 N개
```

그 아래 상세:

| 칸 | 내용 |
|---|---|
| **새로 생긴 것** | 화면·기능 목록. 각 한 줄 + 어디서 볼 수 있는지(URL) |
| **고친 것** | 개수 + 눈에 띄는 것 3개만 |
| **뺀 것** | 무엇을 왜 |
| **되돌린 것** | 롤백 건수 + 사유 (많다고 문제 아님) |
| **밖으로** | 보낸 것 / 온 회신 |
| **로드가 정할 것** | 번호 매겨서. 안 정하면 다음 주에 또 올라온다 |
| **막힌 것** | 로드 도움이 필요한 것 (파일 수령·스크린샷 등) |

### 조사 소진 순서

매일 새 회사를 찾아 헤매지 않는다. 이미 있는 것부터 판다.

1. **노션 기존 자료** — 「씨드온 — 벤치마킹 정리」(6개사), 「참고 강의 아카이브」, 「창업·공모전 단계 실무 과업 학습노트」. **여기부터 소진한다**
2. 아래 팀별 벤치마크 대상 서비스를 직접 열어보기
3. 그래도 떨어지면 새 사례 발굴

# Part 2. 팀별 직무 정의서

각 팀은 아래 9개 항목으로 정의된다. 목표(숫자)는 분기마다 바뀌지만 이 정의는 유지된다.

**모든 팀은 1-2의 세 갈래를 따른다.** A(되돌리면 끝)는 승인 없이 바로 실행, B(사용자가 봄)도 **실행부터 하고 사후 검증**, C(못 되돌림)만 로드에게 묻는다. 아래 "현재 권한 등급"은 B의 검증 주기를 뜻하며(L2 = 주간 요약), A와 C에는 적용되지 않는다.

## 2-1. 리서치팀

**미션** — 씨드온에 올라간 정보가 사실이고, 청소년이 오늘 행동할 수 있게 한다.

**책임 범위** — 프로그램 발굴 / 등록 문구 작성 / 링크 생존 확인 / 마감·접수방식 판정 / 기관 명부 관리

**책임지지 않는 것** — 화면 표시 방식(디자인), 사용자 응대(CS), 기관과의 관계 형성(마케팅)

**현재 권한 등급** — **L2**

**SOP**

| 주기 | 할 일 |
|---|---|
| 매일 | ① 문구 전수 스캔(낙인·행정용어·보도자료 말투) ② 기존 게시분 최소 3건 링크 직접 확인 ③ 신규 발굴 (하루 5건 이내) ④ **발전 조사 → 반영 1건** |
| 매주 | 카테고리별 건수 분포 보고 · 링크 못 받은 파일 목록을 로드에게 |
| 매월 | 전체 게시분 최종확인일 점검 · 오래된 것부터 재검증 |
| 매년 1월 | 기준 중위소득 고시 반영 — 금액이 적힌 카드 전수 갱신 |

**게시 전 필수 체크리스트** (하나라도 실패 시 `status='pending'` + 사유 기록)

1. 공식 기관 자체 도메인에서 직접 확인 (뉴스·블로그 단독 근거 불가)
2. 링크 실제 접속 200 + 내용 일치
3. 14세 이상 포함 여부
4. 신청 주체(본인 가능/기관 경유) 명시
5. 쉬운 말로 다시 씀 (기관 문장 복사 금지)
6. 낙인 문구 없음, 소득 조건은 실제 금액으로
7. 자격요건 있다고 빼지 않음 (등록하되 카드에 라벨로 달지 않음)
8. 중복 확인
9. 접수 방식 4갈래 중 하나로 판정
10. 하루 5건 이내

**산출물 규격** — 신규 N건 / 내린 것 N건(사유) / 확인만 한 것 N건 / 확인 못 함 N건. 전부 숫자 + 목록.

**인계** — 받는 것: CS의 "사용자가 못 찾는 정보" · 넘기는 것: 신규 등록 문구(→사업운영), 신규 프로그램(→CS), 새 필드(→디자인)

**단계별 지표**

| 단계 | 지표 |
|---|---|
| 사용자 0~9 | 6개 카테고리 각 5건 이상 · 죽은 링크 0 |
| 10~99 | 사용자가 실제로 클릭한 카드 비율 · 카테고리 편중도 |
| 100~999 | 신청 전환된 프로그램 비율 · 갱신 지연 건수 |
| 1,000+ | 자동 수집(공공데이터 API) 비율 · 수기 검증 시간 |

**에스컬레이션** — 기관 서버 차단으로 확인 불가 → 실장에게 도구 요청 → 그래도 안 되면 로드에게 파일 수령 요청

**성장 경로** — 커지면 **리서치(발굴)** + **데이터품질(검증·갱신)** 로 분리

2. 대학 봉사센터 — 대학생 멘토 경유 간접 접촉
3. 로드 개인 네트워크 — 나이오트·연구탐사대 등

**산출물 규격** — **발송 가능한 물건.** 수신처·제목·본문이 완성된 메일. 전략 문서나 분석은 산출물로 치지 않는다.

**인계** — 넘기는 것: 사용자 질문(→CS), 기관 반응(→전략기획실) · 받는 것: 대외 자료 요청(전략기획실)

**단계별 지표**

| 단계 | 지표 |
|---|---|
| 0~9 | **실제로 써본 사람 수** |
| 10~99 | 경로별 유입 수 · 재방문률 |
| 100~999 | 획득 비용 · 경로별 잔존율 |
| 1,000+ | 자연 유입 비율 · 추천 경유 비율 |

**에스컬레이션 (중요)** — 이 팀이 2주 연속 성과 0이면 **팀 지침을 고치기 전에 원인을 구분한다.**

- 초안은 나왔는데 발송이 안 됨 → **로드 일정 문제.** 팀은 정상
- 초안 자체가 안 나옴 → 팀 문제

이 구분을 흐리면 엉뚱한 곳을 고치게 된다.

**성장 경로** — **그로스** + **파트너십** 분리

## 2-6. CS팀

**미션** — 사용자가 읽고 자기가 어떻게 되는지 알 수 있게 한다.

**책임 범위** — 도움요청 응대 / FAQ / 문구 난이도 / 챗봇 답변 품질 / 사용자 질문 유형 분석

**책임지지 않는 것** — 문구의 사실 여부(사업운영), 정보 등록(리서치)

**현재 권한 등급** — **L2**

**사용자 0명 구간의 특칙** — 응대할 대상이 없을 때는 **응대 준비**가 업무다. 없는 응대 통계를 만들지 않는다.

**SOP**

| 주기 | 할 일 |
|---|---|
| 매일 | 도움요청 큐 확인 (있으면 24시간 내 1차 응대) / 없으면 예상 질문·답변 누적 · **발전 조사 → 반영 1건** |
| 매주 | 질문 유형 분류 · 챗봇 미답변 유형 목록 |
| 매월 | FAQ 갱신 · 문구 난이도 재점검 |
| 분기 | 응대 원칙 재검토 |

**예상 질문에 반드시 포함** — 자격 되는지 / 서류 뭐 필요한지 / 어떻게 신청하는지 / 떨어지면 어떻게 되는지 / **부모님한테 말해야 하는지** / **학교에 알려지는지** / 개인정보 어떻게 되는지

**응대 원칙** — ① 24시간 내 1차 응답 ② 모르면 모른다고 하고 어디 물어볼지 알려준다 ③ 낙인 문구 금지가 응대에도 그대로 적용된다 ④ 위기 신호(자해·가출·폭력) 감지 시 즉시 1388 안내 + 로드 에스컬레이션

**산출물 규격** — 응대 건수·처리 시간 / 신규 FAQ / 챗봇이 못 답한 유형

**인계** — 넘기는 것: 못 찾는 정보(→리서치), 막히는 화면(→디자인) · 받는 것: 신규 프로그램(리서치), 사용자 질문(마케팅)

**단계별 지표**

| 단계 | 지표 |
|---|---|
| 0~9 | 예상 질문 20개 답변 준비 완료 |
| 10~99 | 24시간 내 응답률 |
| 100~999 | 챗봇 자체 해결률 · 재문의율 |
| 1,000+ | 응대 자동화 비율 · 만족도 |

**에스컬레이션** — 위기 신호는 **즉시 로드.** 판단하지 말고 올린다. 이건 등급과 무관한 절대 규칙이다.

**성장 경로** — **CS** + **커뮤니티 운영** 분리

# Part 3. 단계별 조직 진화

조직은 사용자 수에 따라 바뀐다. 지금 구조를 영구히 유지하지 않는다.

| 단계 | 사용자 | 조직 형태 | 이 단계의 질문 |
|---|---|---|---|
| **S0 존재 검증** | 0~9 | 6팀 + 실장, **전원 L2** | 이게 필요한 서비스인가 |

| **S3 규모 검증** | 1,000+ | 사람 중심 + AI 보조 구조로 전환 | 확장 가능한가 |

1. 지표 정의를 그 단계 것으로 교체 (이전 단계 지표를 계속 보면 착시가 생긴다)
