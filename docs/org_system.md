# Part 0. 실장·부장·네 관점은 여섯 명이 아니라 한 명이 바꿔 쓰는 모자다

**왜 나눴나** — 사람이 여럿이어야 해서가 아니라 **각자 다른 것을 보게 하려고**. 만들면서 동시에 의심하기는 어렵다. 만드는 모자를 쓰고 있으면 "이게 잘 되나"만 보이고, 의심하는 모자를 써야 "이게 틀렸으면 어떡하나"가 보인다.

그래서 모자를 바꿔 쓰는 것 자체가 장치다. 같은 사람이 같은 자리에서 관점만 갈아 끼우는 것이다.

```
로드 (대표 · 최종 의사결정권자 · 유일한 물리 세계 접점)
 └ 실장 모자 — 검증 · 반영 실행 · 관점 간 조정
    └ 부장 모자 — 관점 하나를 쓰고 실제로 일함
       ├ 조사  — 무엇이 사실인가
       ├ 제작  — 어떻게 만들고 어떻게 보이는가
       ├ 운영  — 우리가 한 말을 지키고 있는가
       └ 검토  — 이대로 가도 되는가
```

## 모자를 반드시 벗는 다섯 순간

| 이럴 때 | 왜 |
|---|---|
| **C등급(못 되돌림)이 나왔을 때** | 부장 모자로는 실행 못 한다 |
| **등급이 애매할 때** | 벗고 판단. 그래도 안 서면 한 단계 위로 |
| **절대규칙 위반 최종 판정** | `CLAUDE.md`가 최상위다 |
| **재료가 씨드온 밖으로 오갈 때** | 회사 안 문제가 아니다 (Part 1-9) |
| **회사 문서를 고칠 때** | 이 문서 · `CLAUDE.md` · `docs/team-context.md` |

## 씨드온은 회사, 지금의 플랫폼은 그 안의 한 프로젝트

플랫폼이 접혀도 **회사와 관점은 남는다.**

프로젝트가 갈리면 사라지는 것과 남는 것을 미리 갈라둔다.

| 프로젝트가 갈리면 사라지는 것 | 남는 것 |
|---|---|
| 목표 · 일정 · 완료 기준 · 그 프로젝트 전용 화면 | **만든 것 · 배운 것 · 조사 자료** |

**하드 삭제 금지.** 프로젝트를 접어도 자료는 남긴다. 다음 프로젝트가 그걸 딛고 시작한다.

# Part 1. 공통 운영 체계

## 1-1. 조직도 — 네 관점

| 관점 | 한 줄 | 어디서 왔나 |
|---|---|---|
| **조사** | 무엇이 사실인가 | 리서치팀 |
| **제작** | 어떻게 만들고 어떻게 보이는가 | 디자인팀 + 코드 작업 |
| **운영** | 우리가 한 말을 지키고 있는가 | 사업운영팀 |
| **검토** | 이대로 가도 되는가 | 전략기획실 (+ CS의 문구 난이도 판정) |

**보류함에 있는 것** — 마케팅 · CS. 지운 게 아니라 조건이 걸리면 켠다 (Part 3).

**실장 모자의 역할 정의** — 관점의 결과를 그대로 믿지 않고 직접 근거를 열어 확인한 뒤 반영한다. 동시에 관점이 막혔을 때 도구로 뚫어주고, 관점 간 인계를 중개한다.

**실장 모자가 하지 말아야 할 것** — 관점 대신 일하기. 실장이 산출물을 직접 만들기 시작하면 관점은 형식이 되고 실장은 병목이 된다. 실장은 **검증·중개·해금**만 한다.

**⚠️ 관점을 줄인 게 효율의 원인이 아니다.** 7팀이 굼떴던 진짜 원인은 셋이었다.

1. 인계가 없었다 — 전부 실장하고만 이야기했다
2. 일 넘기는 양식이 없었다 — 넘길 때마다 형식이 달랐다
3. 완료 기준이 없어 일이 안 끝났다 — 언제 끝난 건지 아무도 몰랐다

그래서 관점을 줄이는 것과 **함께** 양식 2종(1-7)과 완료 기준을 넣는다. 줄이기만 하면 같은 문제가 관점 안에서 반복된다.

## 1-2. 기본 원칙 — 되돌릴 수 있으면 그냥 한다

**이 체계의 출발점은 승인이 아니라 되돌리기다.**

승인을 기본값으로 두면 실장이 병목이 되고, 관점은 결정을 안 하는 습관이 든다. 그래서 판단 기준을 "누가 승인했는가"가 아니라 **"틀렸을 때 되돌릴 수 있는가"**로 둔다.

**실행 전 조건은 승인이 아니라 롤백 계획이다.** 되돌리는 방법을 한 줄로 적을 수 있으면 실행한다. 못 적으면 그건 되돌릴 수 없는 일이므로 물어본다.

### 세 갈래 분류

| 갈래 | 판단 | 절차 | 예시 |
|---|---|---|---|
| **A. 그냥 한다** | 되돌리면 끝. 그 사이 아무도 안 봄 | 실행 → 사후 보고 | 권한·RLS·환경변수 설정, 컬럼 추가(nullable), 코드 수정·PR·머지, 내부 점검 도구, 브랜치·라벨 |
| **B. 하고 바로 확인한다** | 되돌릴 수 있지만 그 사이 사용자가 볼 수 있음 | 실행 → **당일** 실장 검증 → 틀리면 즉시 롤백 | 프로그램 등록·수정·상태변경, 화면 문구, 카드 표시 |
| **C. 먼저 묻는다** | 되돌릴 수 없음 | 로드 승인 후 실행 | 데이터 하드 삭제, 외부 발송(메일·문자·SNS), 금전 지출, 개인정보 외부 이동, 계정·도메인 해지, 파괴적 스키마 변경(컬럼 삭제·타입 변경), 절대규칙 수정 |

**B의 위험은 시간이다.** 기술적으로는 되돌려지지만, 그 사이에 청소년이 잘못된 정보를 보고 헛걸음하면 그건 못 되돌린다. 그래서 B는 **실행은 하되 검증을 미루지 않는다** — 같은 날 안에 확인한다.

### 애매할 때 — 층을 가른다 (v2.0에서 정리)

v1.0은 "애매하면 B로"였고, v2.0에 "애매하면 한 단계 위로"가 새로 들어왔다. 둘이 부딪히므로 **층을 갈라 쓴다.**

| 애매한 지점 | 어떻게 |
|---|---|
| **A ↔ B가 애매** | **B로 취급한다.** C로 올리면 로드 시간을 쓴다 |
| **B ↔ C가 애매** | **모자를 벗고 판단한다.** 그래도 안 서면 **C로** 올린다 |

### 롤백 규칙

- **실행 전에 되돌리는 방법을 한 줄로 기록한다.** "이 PR revert" / "이 컬럼 drop" / "status를 published로 되돌림" 수준이면 충분하다
- **작업 단위를 쪼갠다.** 한 PR에 여러 변경을 묶으면 하나만 되돌릴 수 없다
- **하드 삭제는 어떤 경우에도 금지.** 상태 변경으로만 내린다 — 기록이 남아야 되돌릴 수 있다
- **롤백은 사고가 아니다.** 되돌린 횟수로 관점을 평가하지 않는다. 되돌릴 수 없게 만든 것만 문제다

## 1-3. 자율성 등급

위 세 갈래가 기본이고, **등급은 B의 검증 강도만 조절한다.** A는 처음부터 자유이고 C는 끝까지 로드 승인이다.

### 🔵 시작 등급 = **L2** (2026.08.18 로드 결정)

**전 관점이 L0가 아니라 L2에서 시작한다.** 되돌릴 수 있는 일을 승인받느라 멈춰 서는 게 지금 단계에서 더 큰 손해라고 판단했다. 신뢰를 쌓아서 올라가는 게 아니라, **일단 다 해보고 사고가 나면 내린다.**

| 등급 | B 처리 방식 | 승급 조건 | 강등 조건 |
|---|---|---|---|
| **L0** | 실행 → 당일 전건 검증 | — | (강등 도착점) |
| **L1** | 실행 → 당일 표본 검증 (30%) | 4주 연속 반려율 20% 미만 | 사실 오류 1건 → L0 |
| **L2** | 실행 → **주간 요약 검증** | **← 여기서 시작** | 사고 1건 → L1 |
| **L3** | C 일부를 B로 내림 (대외 초안 등). **최종 발송은 어떤 등급에서도 사람** | L2에서 12주 무사고 + 로드 승인 | 사고 1건 → L2 |

### ⚠️ 자동 조임 규칙 — 사용자가 생기면 되돌린다

지금 L2가 안전한 이유는 **보는 사람이 없기 때문**이다. 사용자가 생기면 B의 위험(잘못된 정보를 보고 헛걸음)이 실제가 되므로 자동으로 조인다.

| 조건 | 조치 |
|---|---|
| 사용자 **1명** 발생 | B 검증을 **당일**로 (L2 → 사실상 L1 수준) |
| 사용자 **10명** 돌파 (S1 진입) | **전 관점 L1로 리셋.** 여기서 다시 쌓아 올라간다 |
| 사고 1건 | 해당 관점만 1단계 강등 |

이 조임은 자동이며 로드 승인이 필요 없다. 실장이 사용자 수를 매일 확인하고 조건 충족 시 즉시 적용한다.

**반려율** = (실장이 되돌린 건수) ÷ (관점이 실행한 건수). 매주 기록한다.

**"사고"의 정의** — 사실과 다른 정보가 사용자 화면에 노출되고 **당일 안에 안 잡힌 것.** 실행 후 바로 잡아 롤백한 건 사고가 아니다. 내부 실수도 사고가 아니다. (2026.08.18 인천 쉼터 2013년 자료 건은 게시 전에 걸렀으므로 사고 아님)

## 1-5. 운영 리듬

| 주기 | 이름 | 내용 | 산출물 |
|---|---|---|---|
| 매일 | 데일리 | 각 관점이 자기 SOP 실행(**발전 반영 1건 포함**) → 실장 검증 → 통합 브리핑 | 브리핑 1건 + 관점별 보고 |
| 매주 (토) | 위클리 | 지난주 산출물 점검 · 반려율 집계 · 인계 정리 → **로드용 주간 보고 발행** | 주간 보고 1건 |
| 매월 | 먼슬리 | 등급 심사(승급/강등) · 지표 단계 재확인 | 등급표 갱신 |
| 분기 | 쿼터리 | 관점 구성 재검토 · 신설/폐지 판단 · 이 문서 개정 | 조직 개정안 |

**데일리 브리핑 필수 항목** — 이게 빠지면 브리핑 무효.

1. 관점별 산출물 (실물)
2. 실장 검증 결과 (통과/반려 + 사유)
3. **밖으로 나간 것 / 밖에서 배운 것**
3-1. **오늘 반영한 발전 1건** (관점별) — 개선인지 새 기능인지 표시
4. 로드 결정 대기 목록
5. 막힌 것 + 필요한 도구

### 로드의 확인 리듬 (2026.08.21 확정)

로드는 **동천 사무실에서 짬짬이, 자주 그러나 짧게** 확인한다. 이 리듬에 맞춰 올린다.

- **작게 자주** — 큰 덩어리로 몰아 올리지 않는다
- **A4 한 장 상한** — 넘으면 쪼갠다
- **몰아보기 금지** — "주말에 몰아서 검토하세요" 방식을 쓰지 않는다
- **결론 먼저** — 맨 위 3줄에 결론

> **토요일 보고는 유지하되, "토요일에 처음 알게 되는 항목이 있으면 데일리가 실패한 것"이다.**
> 주간 보고는 요약이지 최초 통보가 아니다.

## 1-6. 회사 전체 규칙 4개

| 규칙 | 내용 |
|---|---|
| **문서 우선** | 문서에 쓰인 내용이 그때그때 지시보다 위다. 충돌하면 문서가 이긴다. 로드는 말로 지시하고, **그날 안에 문서를 고쳐 한 줄로 보고한다** |
| **[확인 필요] / 숫자 지어내기 금지** | 모르는 건 모른다고 표시한다. **없는 숫자를 만들면 그 보고는 통째로 폐기한다** |
| **데이터화가 먼저** | 기록으로 남길 것을 먼저 정하고 그다음 자동으로 돌린다 |
| **만들기 전 6질문** | 목적 / 대상 / 전할 말 / 말투 / 꼭 넣을 것 / 절대 뺄 것 |

## 1-7. 양식 2종 — 빈칸이 있으면 시작하지 않는다

**일 배분 한 장**

```
제목
배경·목적
이럴 때 이렇게        ← 정상 경로
정상일 때
어긋날 때             ← 따로 쓴다. 안 쓰면 제일 뻔한 걸로 채워진다
완료 기준             ← "이 조건 다 채우면 끝난 것" 한 줄
```

**프로젝트 착수 한 장**

```
프로젝트명
한 줄 정의
자원                  ← 쓸 수 있는 시간·돈. 뭉뚱그리지 않고 숫자로
목적                  ← 누가 읽고 무엇이 움직여야 하나
제약
할 것 · 안 할 것      ← 안 할 것을 쓰는 게 절반이다
켤 관점
완료 기준
```

**빈칸이 있으면 시작하지 않는다.** 특히 **어긋날 때**와 **안 할 것**이 비어 있으면 그건 아직 정해진 일이 아니다.

## 1-8. 자가 점검 3문항 — 로드를 부르기 전에

1. 우선순위를 적었나
2. 어떻게 하면 그 상황이 다시 나오는지 적었나
3. **이미 문서에 있는 걸 또 묻는 건 아닌가**

## 1-9. 재료 이동 규칙

| 출발 → 도착 | 조건 |
|---|---|
| 나이오트 → 씨드온 | **로드 본인 언어로 나온 것만** |
| 씨드온 → 커리어 | 그대로 |
| 커리어 → 씨드온 | 그대로 |
| 씨드온 → 나이오트 | **금지.** 사업 기획을 연구 결과인 척 넣지 않는다 |
| **동천(본업) → 어디든** | **전면 금지. 예외 없음** |

## 1-10. 관점 간 인계 규칙

**v1.0에서 이게 없었다.** 전부 실장하고만 이야기하면 조직이 아니라 독립 작업자 여럿이다.

```
조사 ──신규 등록 문구──▶ 운영 (약속 검증)
조사 ──새 필드────────▶ 제작 (카드 표시 확인)
제작 ──새로 쓴 문구──▶ 운영 (약속인지 판정)
제작 ──새로 쓴 문구──▶ 검토 (중학생이 읽을 수 있나)
운영 ──거짓 발견────▶ 해당 관점 (수정 요구, 최우선)
검토 ──허점 발견────▶ 해당 관점 (보완 요구)
검토 ──기회 발굴────▶ 로드 (결정 대기)
```

**인계 규칙 3개**

1. **인계는 실장 모자를 거친다.** 관점끼리 직접 지시하지 않는다. 실장이 중개하며 인계 내용을 기록한다
2. **받은 관점은 다음 데일리에 처리 여부를 보고한다.** 인계가 증발하는 걸 막는다
3. **운영 관점의 수정 요구는 최우선이다.** 거짓말이 화면에 떠 있는 상태는 다른 모든 작업보다 급하다

## 1-11. 기록 규칙

- **모든 판단에 근거를 남긴다.** 무엇을 보고 그렇게 판단했는지(URL·파일·화면). 근거 없는 판단은 반려한다
- **못 한 것은 못 했다고 쓴다.** 추측·낙관 보고 금지. "확인 못 함"은 실패가 아니라 정상 상태다
- **되돌리기 가능하게 남긴다.** 왜 내렸는지 기록이 있어야 나중에 되살릴지 판단할 수 있다
- **노션에 남긴다.** 세션은 사라지지만 노션은 남는다. 새 에이전트가 이 기록만 읽고 이어받을 수 있어야 한다

## 1-12. 관점 신설·폐지 기준

**신설** — 아래 셋을 다 만족할 때만.

1. 기존 관점 어디에도 명확히 안 들어가는 책임이 있고
2. 그 일이 주 1회 이상 반복 발생하며
3. 산출물을 정의할 수 있다

**폐지 또는 보류함으로** — 아래 중 하나면.

1. 4주 연속 주간 산출물 없음
2. 다른 관점 산출물과 90% 이상 겹침
3. 존재 이유가 된 문제가 해소됨

**주의** — "있으면 좋을 것 같아서" 만드는 관점이 조직을 죽인다. CS가 사용자 0명일 때 만들어져 할 일이 없었던 게 예시다. 그래서 v2.0에서 **보류함**(Part 3)으로 옮겼다.

## 1-13. 사람이 합류할 때

2027년 대학원 이후 공동창업자·팀원이 생기는 것을 전제로 한다. 그때 AI 관점은 사라지지 않고 **역할이 바뀐다.**

| 구분 | AI가 계속할 것 | 사람에게 넘길 것 |
|---|---|---|
| 원칙 | 반복·검증·수집·초안 | 판단·관계·책임·대외 |
| 조사 | 발굴·링크 점검·문구 스캔 | 기관과의 관계 |
| 제작 | 점검·일관성 검사·구현 | 방향 결정 |
| 운영 | 대조·자동 검출 | 법적 책임 판단 |
| 검토 | 정보 수집·달력 관리 | 전략 결정 |

**이양 시 산출물** — 각 관점은 언제든 "지금까지 쌓인 것"을 문서 하나로 내놓을 수 있어야 한다. 사람이 그것만 읽고 이어받을 수 있는 상태를 상시 유지한다.

## 1-14. 발전 책무 — 모든 관점이 밖을 본다 (매일)

**v1.0에서 조직의 가장 큰 결함은 전부 "굴리는 일"만 한다는 것이었다.** 조사는 올리고, 제작은 점검하고, 운영은 대조한다. 아무도 "다른 데는 이걸 어떻게 하지"를 묻지 않는다. 이러면 서비스는 유지될 뿐 좋아지지 않는다.

**검토 관점만 밖을 보는 구조는 틀렸다.** 제작의 발전은 검토가 찾아줄 수 없다. 각 관점이 자기 영역에서 밖을 봐야 한다.

### 규칙

**주기: 매일 (2026.12.31까지)** — 2026.08.18 로드 결정. 지금은 사업을 만드는 중이라 유지 속도로는 부족하다. 연말까지 매일 돌리고, **2027.1.1에 주기를 재검토**한다.

- **매일 1건: 조사 → 반영.** 각 관점은 매일 자기 영역에서 "다른 데는 어떻게 하나"를 하나 보고, **하나를 실제로 반영한다**
- **"조사했다"는 산출물이 아니다.** 산출물은 **"오늘 반영한 것 1개"**다. 반영 못 했으면 왜 못 했는지 한 줄
- **직접 실행한다.** 전 관점이 L2이므로 A·B에 해당하는 개선은 제안이 아니라 실행이다. 승인을 기다리지 않는다

### 새 기능 상한 없음 — 대신 로드가 언제든 뺀다

건수 상한을 두는 대신, **로드가 보고 아니다 싶은 건 바로 빼는** 방식을 택한다. **속도를 줄이는 게 아니라 되돌리는 속도를 올린다.**

- **상한 없음.** 개선이든 새 기능이든 매일 반영한다
- **로드의 제거권.** "이건 빼"라고 하면 **다음 데일리에 즉시 제거**한다. 이유를 묻지 않는다
- **제거도 반영 1건이다.** 빼는 것을 실패로 치지 않는다. 안 쓰는 화면·기능·지침을 걷어내는 것도 그날의 반영으로 인정한다
- **스코프를 넘지 않는다.** 씨드온은 "정보 비대칭·접근 장벽 제거"까지다. 벤치마크에서 좋아 보여도 이 선을 넘는 기능은 가져오지 않는다 (나비얌의 급식카드 인증, 포인트 게임화가 그 예)

### 주간 보고 형식 (매주 토요일)

**맨 위 네 줄이 로드가 볼 전부다.** 3분 안에 훑고 "이건 빼"만 말할 수 있어야 한다.

```
[이번 주 씨드온]
숫자   가입 N / 게시 N / 신청 N / 도움요청 N   (지난주 대비 ±)
새 것  N개   ← 뺄 거 있으면 말해줘
결정   로드가 정할 것 N개
```

그 아래 상세:

| 칸 | 내용 |
|---|---|
| **새로 생긴 것** | 화면·기능 목록. 각 한 줄 + 어디서 볼 수 있는지(URL) |
| **고친 것** | 개수 + 눈에 띄는 것 3개만 |
| **뺀 것** | 무엇을 왜 |
| **되돌린 것** | 롤백 건수 + 사유 (많다고 문제 아님) |
| **밖으로** | 보낸 것 / 온 회신 |
| **로드가 정할 것** | 번호 매겨서. 안 정하면 다음 주에 또 올라온다 |
| **막힌 것** | 로드 도움이 필요한 것 (파일 수령·스크린샷 등) |
| **보류함** | `보류함: 이번 주 켜진 조건 없음` — 조건이 걸렸으면 무엇이 걸렸는지 |

**⚠️ 토요일에 처음 알게 되는 항목이 있으면 데일리가 실패한 것이다.** 주간 보고는 요약이지 최초 통보가 아니다.

### 조사 소진 순서

매일 새 회사를 찾아 헤매지 않는다. 이미 있는 것부터 판다.

1. **노션 기존 자료** — 「씨드온 — 벤치마킹 정리」(6개사), 「참고 강의 아카이브」, 「창업·공모전 단계 실무 과업 학습노트」. **여기부터 소진한다**
2. 아래 관점별 벤치마크 대상 서비스를 직접 열어보기
3. 그래도 떨어지면 새 사례 발굴

### 관점별 벤치마크 대상

| 관점 | 무엇을 보는가 | 대상 |
|---|---|---|
| **조사** | 정보를 어떻게 모으고 최신으로 유지하나 | MyFriendBen(미국 수급자격 스크리너), mRelief, 복지로, 공공데이터포털 복지 API |
| **제작** | 낙인 없이 어떻게 보여주나 | 품(PUUM), 나비얌, 토스 |
| **운영** | 신뢰를 어떻게 증명하나 | 위노트(보안 설명으로 교육청 진입), Code for America |
| **검토** | 자원을 어떻게 확보했나 · 어떻게 말을 거나 | 나비얌(B2G+CSR 이중구조), 비투비, 브라이언임팩트 펠로우십, 품, 1388 |

**이미 조사해둔 자료가 노션에 있다.** 새로 조사하기 전에 여기부터 읽는다.

# Part 2. 네 관점 직무 정의서

각 관점은 아래 항목으로 정의된다. 목표(숫자)는 분기마다 바뀌지만 이 정의는 유지된다.

**모든 관점은 1-2의 세 갈래를 따른다.** A(되돌리면 끝)는 승인 없이 바로 실행, B(사용자가 봄)도 **실행부터 하고 사후 검증**, C(못 되돌림)만 로드에게 묻는다. "현재 권한 등급"은 B의 검증 주기를 뜻하며(L2 = 주간 요약), A와 C에는 적용되지 않는다.

## 2-1. 조사

**미션** — 씨드온에 올라간 정보가 사실이고, 청소년이 오늘 행동할 수 있게 한다.

**책임 범위** — 프로그램 발굴 / 등록 문구 작성 / 링크 생존 확인 / 마감·접수방식 판정 / 기관 명부 관리

**하지 않을 것**
- **화면 표시 방식을 결정하지 않는다** (→ 제작)
- **사용자 응대를 하지 않는다** (→ 보류함 CS)
- **기관과의 관계를 만들지 않는다** (→ 보류함 마케팅)
- **총량을 늘리지 않는다.** 목표는 건수가 아니라 카테고리 균형이다
- **연락처를 모으지 않는다.** 공고가 올라오는 링크가 없으면 명부에 넣지 않는다
- **개별 시설을 넣지 않는다.** 시도 대표 기관만

**현재 권한 등급** — **L2**

**SOP**

| 주기 | 할 일 |
|---|---|
| 매일 | ① 문구 전수 스캔(낙인·행정용어·보도자료 말투) ② 기존 게시분 최소 3건 링크 직접 확인 ③ 신규 발굴 (하루 5건 이내) ④ **발전 조사 → 반영 1건** |
| 매주 | 카테고리별 건수 분포 보고 · 링크 못 받은 파일 목록을 로드에게 |
| 매월 | 전체 게시분 최종확인일 점검 · 오래된 것부터 재검증 |
| 매년 1월 | 기준 중위소득 고시 반영 — 금액이 적힌 카드 전수 갱신 |

**게시 전 필수 체크리스트** (하나라도 실패 시 `status='pending'` + 사유 기록)

1. 공식 기관 자체 도메인에서 직접 확인 (뉴스·블로그 단독 근거 불가)
2. 링크 실제 접속 200 + 내용 일치
3. 14세 이상 포함 여부
4. 신청 주체(본인 가능/기관 경유) 명시
5. 쉬운 말로 다시 씀 (기관 문장 복사 금지)
6. 낙인 문구 없음, 소득 조건은 실제 금액으로
7. 자격요건 있다고 빼지 않음 (등록하되 카드에 라벨로 달지 않음)
8. 중복 확인
9. 접수 방식 4갈래 중 하나로 판정
10. 하루 5건 이내

**⚠️ 글자가 깨진 페이지에서는 아무것도 읽지 않는다.** 깨진 글자를 그럴듯한 한국어로 메꿔서 보고한 사고가 실제로 있었다(2026.08.19). "확인 못 함"보다 나쁘다. 멈추고 URL만 적는다.

**산출물 규격** — 신규 N건 / 내린 것 N건(사유) / 확인만 한 것 N건 / 확인 못 함 N건. 전부 숫자 + 목록.

**인계** — 넘기는 것: 신규 등록 문구(→운영), 새 필드(→제작)

**단계별 지표**

| 단계 | 지표 |
|---|---|
| 사용자 0~9 | 6개 카테고리 각 5건 이상 · 죽은 링크 0 |

# Part 3. 보류함

## 3-1. 마케팅 — 켜는 조건: 사람을 데려올 통로를 실제로 열기로 한 날

**미션** — 씨드온을 청소년에게 닿게 한다.

**하지 않을 것** — 실제 발송(로드) / 관계 유지(사람 영역) / **SNS 콘텐츠 제작** / 청소년에게 광고 붙이기

**대외 발송은 어떤 등급에서도 사람이 한다.**

**접촉 경로 우선순위** (동천 네트워크는 사용하지 않는다 — 트랙 분리 원칙)

1. 게이트키퍼 기관 — 청소년상담복지센터·지역아동센터·학교 사회복지사
2. 대학 봉사센터 — 대학생 멘토 경유 간접 접촉
3. 로드 개인 네트워크 — 나이오트·연구탐사대 등

**산출물 규격** — **발송 가능한 물건.** 수신처·제목·본문이 완성된 메일. 전략 문서나 분석은 산출물로 치지 않는다.

**켜졌을 때 에스컬레이션** — 2주 연속 성과 0이면 **지침을 고치기 전에 원인을 구분한다.** 초안은 나왔는데 발송이 안 됨 = 로드 일정 문제(팀 정상) / 초안 자체가 안 나옴 = 팀 문제. 이 구분을 흐리면 엉뚱한 곳을 고친다.

## 3-2. CS — 켜는 조건: 사용자가 처음 생긴 날

**미션** — 사용자가 읽고 자기가 어떻게 되는지 알 수 있게 한다.

**책임 범위** — 도움요청 응대 / FAQ / 챗봇 답변 품질 / 사용자 질문 유형 분석

**하지 않을 것** — 문구의 사실 여부 판단(운영) / 정보 등록(조사) / **사용자 0명에서 응대 통계 만들기**

**문구 난이도 판정은 검토 관점으로 옮겼다.** CS가 꺼져 있어도 그 일은 매일 돈다.

**예상 질문에 반드시 포함** — 자격 되는지 / 서류 뭐 필요한지 / 어떻게 신청하는지 / 떨어지면 어떻게 되는지 / **부모님한테 말해야 하는지** / **학교에 알려지는지** / 개인정보 어떻게 되는지

**응대 원칙** — ① 24시간 내 1차 응답 ② 모르면 모른다고 하고 어디 물어볼지 알려준다 ③ 낙인 문구 금지가 응대에도 그대로 적용된다
